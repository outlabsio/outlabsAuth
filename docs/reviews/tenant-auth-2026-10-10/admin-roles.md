# Independent review: administrative roles and target-bound grants

Reviewed on 2026-10-10. Proposal and review-packet revision **0.1**. Source commit **58230e25ceb373302dc48e167f1dbbe60197d393**. Lane: authorization, administrative roles, delegation, query boundaries and their lifecycle/cache dependencies. The worktree was clean initially and after the executable checks. A later final status check showed a concurrent modification to the proposal document, with HEAD unchanged; that later edit is outside this review. All source/line references identify the frozen reviewed commit. This review was completed independently, without reading other reviewers' findings.

## Verdict

**Revise the conditioned-decision cache contract before the affected authorization implementation and activation gate.** One High finding reproduces an existing a36 cached-ABAC failure that must not be inherited by managed administration. The recommended grant model otherwise has a coherent bounded first phase: independent customer roots, separate administrative templates, immutable policy revisions, pinned limited-group admissions, explicitly approved dynamic reach, and non-delegable human grants.

I found no additional contradiction in those recommended defaults after examining exact/subtree/group reach, protected Internal/control-domain trust, platform exclusion, root credential operations, expansion, history/restore and SQL/query contracts. This conclusion assumes the explicitly excluded capabilities remain disabled and the proposal's stated management and activation requirements are implemented. It is a technical recommendation, not human/maintainer acceptance, implementation qualification, publication permission or consumer approval.

The unfinished future runtime is not itself a novel defect. The concrete prototype/baseline differences below are qualification obligations already anticipated by the proposal. Open D decisions are kept separate from the new finding.

## New actionable finding

### F-admin-01: implicit current time is omitted from the cached ABAC decision context

- **Severity:** High, conditional on cached Enterprise ABAC membership authorization. Impact is authorization beyond an enforced condition; occurrence requires a positive cache entry crossing that condition's boundary.
- **Evidence category:** baseline implementation plus proposed acceptance-contract gap. This is not a deployed administrative-grant exploit: the grant evaluator is unwired.
- **Proposal/source revision:** revision 0.1 / commit `58230e25ceb373302dc48e167f1dbbe60197d393`; the affected baseline files match a36.
- **Review lane:** conditions, concurrency/cache, operation-specific authorization.
- **Requirements/use cases:** R10, R13, R14, R19; U13–U14. The condition-currentness obligation is explicit at proposal `:848`. These use cases concern live authority and warm-cache withdrawal; the new case adds withdrawal caused by a time predicate without a policy edit.
- **Decision dependency:** D10 (`docs/TENANT_IDENTITIES_AND_ADMINISTRATIVE_GRANTS.md:1805`), with D03's frozen semantic policy. This does not ask reviewers to reconsider the recommended immutable revisions or immediate durable-state revocation default.

**Claim and exact evidence.** `PermissionService.check_permission` computes the hash and consults its cache at `outlabs_auth/services/permission.py:474` before constructing the evaluated condition context at `:510`. `_permission_cache_context_hash` encodes `time_attrs or {}` at `:1601`. When callers omit `time_attrs`, `PolicyEvaluationEngine.create_context` creates real current-time attributes, including hour, minute and business-hours status, at `outlabs_auth/services/policy_engine.py:352`. Thus the time actually evaluated is absent from the cache key. The normal human dependency passes resource/environment context but no `time_attrs` at `outlabs_auth/dependencies/__init__.py:462`; its environment supplier has no current time at `:49`.

A positive entity-membership result is cached at `outlabs_auth/services/permission.py:595`. The cache checks global/user/entity versions, then returns the old Boolean at `outlabs_auth/services/cache.py:342`; it stores that result for the configured permission TTL at `:380`. No policy/user/entity mutation occurs simply because the clock crosses noon. The same issue can hold a cached denial after the permitted interval opens.

The proposal's cache enumeration at `docs/TENANT_IDENTITIES_AND_ADMINISTRATIVE_GRANTS.md:1142` includes policy, topology and lifecycle epochs but does not expressly include the full evaluated condition context, durable resource version or a condition-specific cacheability/deadline rule. Its validity-deadline rule at `:1149` should explicitly cover ABAC transitions as well as grant windows. Current-state epoch checks and reliable revocation delivery alone do not close this case.

**Counterexample.** A synthetic Customer B West membership role allows `document:update` only when `time.hour < 12`. The user, entity, role, permission and all version counters remain unchanged. At 11:59 UTC, the condition allows and the Boolean is cached. At 12:01 UTC, within a 300-second cache TTL, an otherwise identical request must deny. The inspected implementation returns the cached allow before evaluating current time. A direct fresh evaluation returns false.

**Executed proof.** The focused scratch probe used the real `PermissionService`, `CacheService`, `MemoryCacheBackend` and `PolicyEvaluationEngine`, with a frozen clock and deterministic synthetic replacements for database authority/condition suppliers. Observed results:

```text
before_noon_authorized: true
after_noon_cached_authorized: true
after_noon_fresh_condition_authorized: false
membership_condition_evaluations: [11]
```

The second call did not run the membership condition supplier. Clock advancement was synthetic; no waiting or external infrastructure was involved. The configured TTL exceeds the simulated two-minute interval. This demonstrates the service/cache contract failure, not PostgreSQL row loading, an HTTP endpoint or a consumer deployment.

**Consequence.** A permitted user can continue a conditioned action after its time restriction closes, despite an unchanged and correctly frozen template. Reusing the same incomplete key scheme for staff grants would break the proposed requirement to evaluate the qualifying live path under current trusted conditions. A fixed immutable condition definition does not freeze its resource/environment/time inputs.

**Confidence and assumptions.** High confidence in the source ordering and reproduced cache behavior. Exploitability in any host depends on its enabled ABAC/caching profile and use of time-conditioned entity-membership authority. No host state was inspected. The broader proposed resource/environment cache concern is design reasoning; no persistent administrative cache exists to test.

**Smallest complete correction.** Resolve one server-owned evaluated condition context before cache lookup and bind the cached result to the exact resource/operation, all outcome-bearing trusted attributes and relevant versions. Include generated current-time semantics rather than hashing the caller's absent `time_attrs`. The safe first-phase alternative is to bypass positive and negative decision caching for conditioned paths whose dependencies or transition deadlines cannot be completely bound. A restricted, reviewed time-condition vocabulary may later use proven next-transition deadlines; an arbitrary time bucket or ordinary grant expiry is insufficient. Keep the normal RBAC/policy-loading cache available where it cannot substitute for condition evaluation.

Update proposal section 12.2 and A10 to say this explicitly. Fix the baseline path separately, or deliberately prevent its affected cache mode from being used in qualified administration. The finding is not closed by selecting a locking protocol: locks and durable policy epochs do not change when an environment/time predicate changes.

**Acceptance proof required.** Add a warm-cache test crossing both allow-to-deny and deny-to-allow boundaries while grant/role/user/entity epochs remain constant. Run it for omitted and explicit `time_attrs`, role and permission conditions, direct/detail and list predicates, memory and required Redis profiles. Add two resources at the same entity/action with opposite condition results, plus a resource attribute change between requests. Missing or unversionable context must evaluate freshly or deny; a failed context serializer must never reuse another result. The PostgreSQL/HTTP tests must use actual stored conditions and normal dependencies, beyond this focused supplier-level probe.

**Gate affected.** Clarify the specification before WP04's conditioned-cache contract is accepted. Block WP04/G2 and release/host activation of affected cached conditioned authorization until corrected or excluded. This does not block drafting schema, the non-delegable model itself, or a configuration that evaluates these conditions freshly. Existing a36 consumers using the affected profile need a separate baseline fix decision; no such deployment change was performed here.

**Suggested disposition:** accept the correction and add executable closure evidence. No new architectural decision ID is required for the conservative cache-bypass alternative.
